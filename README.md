# Э-э-э-кспереременты
В данном коде проверяются две возможности:
* Отображение в Swagger UI одного эндпоинта с большим числом схем данных
* Использование GenericViewSet без обращения к БД

## Проблематика
Пусть у нас есть эндпоинт /api/users/, который возвращает список пользователей.
Получения списка достаточно быстрое и отображается во многих местах.
Кроме отображения, этот список ещё используется для полей ввода с автозаполением.
Для полей ввода достаточно 2х полей: `id` и `full_name`.

И вот нам нужно для редко-используемой страницы добавить сумму долга пользователей `debt`. Это поле тяжёлое, т.е. нагружает систему.
Если добавить это поле в существующее API, то все страницы со списком пользователей начнут равномерно нагружать систему, а поля ввода будут создавать кратковременную высокую нагрузку, т.к. запрос отправляется на каждое изменение поля ввода.

Очевидным решением является разделить логику по трём эндпоинтам. Отдельно для автокомплитов, отдельно для простых списков и отдельно для тяжёлых списков.
Но если api предназначено для внешних клиентов, то возникает несколько сложностей. 
* Тяжело найти нужный эндпоинт в большом количестве. 
* Пользователи могут вызвать тяжёлый api, там где нужен лёгкий. 
* Каждому эндпоинту нужно дать понятное и не противоречивое имя.

Альтернативное решение сводится к тому, что все эндпоинты возвращающие одну сущность, объединяются в один эндпоинт.
В этом проекте я проверяю, возможно ли за одним эндпоинтом спрятать несколько разных json-схем, так чтобы их было удобно смотреть в swagger.

## Решения
1. В drf-spectacular есть вспомогательный класс PolymorphicProxySerializer. Но он требует, чтобы у объекта было поле, по которому можно было бы понять структуру объекта. Это имеет смысл, если данные в списке могут быть разными. В нашей задаче, все объекты имеют одинаковую ожидаемую структуру, которую должен передать клиент в запросе.

2. В OpenApi есть механизм версионирования. В запросе можно передать версию, а бекенд должен вернуть структуру соответсвующую этой версии. Этот механизм, можно задействовать для управления схемами. 

Во-первых, это очевидный костыль, т.к. если такой механизм управления схемами, ломает версионирование, если оно есть.
Во-вторых, управление версиями делается на уровне всего swagger, а набор схем у каждого эндпоинта должен быть свой.
В-третьих, drf-spectacular никак не подскасказывает про версии/схемы

3. В OpenApi есть механизм подсказок. С его помощью можно показывать, какой ответ будет для каждой из схем. Эксперимент показал принципиальную возможность реализации множественной схемы для одного эндпоинта.
